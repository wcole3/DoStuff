# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

DoStuff is a VSCode extension built with Bun + esbuild. Two bundles ship from one source tree: `dist/extension.cjs` for the extension host (CommonJS, required by VSCode's loader) and `media/index.js` + `media/styles.css` for the webview UI (browser IIFE). The webview is React 18 with `react-window` v1.8.x for list virtualization. The extension also runs an HTTP MCP server on `127.0.0.1:3947` exposing the active ticket queue to coding agents.

## Commands

- `bun run build` — bundle both extension and webview via esbuild.
- `bun run watch` — same in continuous watch mode.
- `bun test` — run all tests with Bun's built-in test runner.
- `bun test -t "<name>"` — run a single test by name pattern.
- `bun run package` — build, then produce a `.vsix` via `@vscode/vsce`.
- `bun run clean` — remove `dist/` and the webview output files in `media/`.

Press `F5` in VSCode (or `Run and Debug > Run Extension`) to launch an Extension Development Host with the current build.

## Architecture

**Extension host** (`src/*.ts`, excluding `src/webview/`). `extension.ts` is the activation entry point — it registers all seven commands, wires up the sidebar and board providers, and starts/stops the MCP server. `storage.ts` exposes `IssueStore`, which reads/writes one `<id>.json` file per ticket under `<workspace>/.vscode/dostuff/` (falling back to `globalState` when no workspace is open). `sidebarProvider.ts` is a `WebviewViewProvider` for the activity-bar sidebar; `boardProvider.ts` is a singleton `WebviewPanel` for the full-tab board. `mcpServer.ts` runs an HTTP MCP server on `127.0.0.1:3947` with four tools, three resources, and one prompt. `types.ts` is the canonical schema — it defines `Issue`, `Status`, `Priority`, the `HostToWebview` / `WebviewToHost` discriminated unions, `ACTIVE_LANE_CAP = 6`, and the `canMoveToActiveLane` helper. `webviewHtml.ts` builds the CSP-nonced HTML shell. `sampleData.ts` seeds the store on first activation.

**Webview bundle** (`src/webview/*.tsx`). The React 18 entry `index.tsx` reads `window.__DOSTUFF_MODE__` (set by the host shell) and renders either `<Sidebar/>` or `<Board/>`. A shared `<IssueDetail/>` component handles the inline edit panel. `messaging.ts` wraps `acquireVsCodeApi()` and the host-to-webview message stream as a `useSyncExternalStore` hook so React components subscribe without leaking listeners. The sidebar list and the Thinking/Complete drawers in the board use `react-window`'s `FixedSizeList` for virtualization; active board lanes are not virtualized (cap = 6). Drag-and-drop on the board uses the HTML5 native API — no third-party DnD library. **Cross-webview drag** (sidebar→board) is a pseudo-drag: native DnD doesn't reliably cross VSCode's webview iframe boundary, so the sidebar's `dragstart` posts an `externalDragStart` message; the host opens the board if needed and forwards the signal, and the board renders a click-absorbing "Move to *lane*" overlay (`bd-pick-overlay`) inside each lane/drawer. The actual mutation still flows through `setStatus` → `postUpdateIssue` → host `applyIssueUpdate`. Esc cancels.

**Build pipeline.** `scripts/esbuild.config.ts` exports two configs: `extensionConfig` (Node CommonJS target, `vscode` marked external) and `webviewConfig` (browser IIFE target, no externals). `scripts/build-with-esbuild.ts` runs both in parallel; `scripts/watch-with-esbuild.ts` watches both. `vscode` is external in the extension config because VSCode injects the real API at load time. The webview never imports `vscode`. For tests, `tsconfig.json`'s `paths.vscode` alias redirects `import * as vscode from "vscode"` to the hand-rolled `mocks/vscode.ts` — so `tsc` and the IDE see the mock, but the runtime esbuild bundle leaves `vscode` external. Whenever you introduce a new `vscode.*` call in `src/`, add a stub to `mocks/vscode.ts` or test resolution will fail.

### Workflow rules the code enforces

These rules are non-obvious from a fresh read of the code, so they live here:

- **New tickets always land in `Thinking`.** Both the UI new-issue modal and the MCP `create_ticket` tool start them there. Triage is a human action.
- **`update_ticket_status` (MCP) is doubly gated.** Both the current and target status must be in `AGENT_WRITABLE_STATUSES` = {Planned, Working, Verification}. This blocks agents from promoting out of Thinking, from sending tickets back into Thinking, and from touching Complete or Closed in either direction. Humans can promote Thinking → Planned via the UI; agents cannot. The host's `applyIssueUpdate` chokepoint enforces the same rules for UI moves.
- **Active lanes (Planned, Working, Verification) are each capped at 6 open tickets.** The cap is enforced in three places by design: the board UI drop handler (visual rejection + toast for instant feedback), the host's `applyIssueUpdate` (the authority — warning + state revert), and the MCP `update_ticket_status` tool (error response, protecting against an agent racing the UI). All three exist so each layer can refuse independently.
- **`update_ticket_progress` (MCP) only mutates `tasks[].done` and appends one `record` entry.** Title, description, priority, type, and verifyCriteria are immutable through MCP — only the UI can edit those. This is what keeps agents from silently rewriting scope. The status gate is `AGENT_VISIBLE_STATUSES` = {Thinking, Planned, Working, Verification}: agents *can* annotate Thinking tickets (so they can record relationships on a ticket they just filed via `create_ticket`, or leave context for the human before triage), but Complete and Closed are still rejected.
- **Thinking-drawer click is a detail view; Shift+Click is the promote action.** A plain click on a Thinking-drawer card opens the detail overlay (so humans can read the draft before triaging); Shift+Click promotes it to Planned via the same `setStatus` path used by drag. The Complete drawer has no promote shortcut — its cards only ever open the detail overlay.
- **Attachment writes go through the host, never `mergeIssueUpdate`.** Binary files live under `<storagePath>/attachments/<issueId>/<attachmentId><ext>` (sibling of the JSON tickets). The ticket JSON carries only `Attachment` metadata: `{ id, name, mimeType, sizeBytes, addedAt }`. The host's `appendAttachment` helper in `extension.ts` is the only path that mints new entries — `mergeIssueUpdate` reconciles `incoming.attachments` against `prior.attachments` by id and silently drops any unknown id, so the webview can reorder or delete but never inject. Uploads enforce `MAX_ATTACHMENT_BYTES = 10 MB` at the host edge and again at the MCP resource read. Deleting a ticket recursively removes its attachments folder. Image previews use `webview.asWebviewUri()` over an extended `localResourceRoots` pointing at the attachments dir; the URL is composed in the webview from `Settings.attachmentsBaseUri` + `<issueId>/<attachmentId><ext>`. Attachments are served to MCP clients as a new resource template `dostuff://attachments/{ticketId}/{attachmentId}` (base64 `BlobResourceContents`); `publicView()` decorates each `Attachment` with that URI so `get_ticket` lists them. The new-issue modal can stage attachments before the ticket exists: bytes from drag-drop go straight into modal state, while the + button and Remote-WSL URI drops round-trip through `pickAttachmentForStaging` / `stageAttachmentByUri` → host helpers `onPickForStaging` / `onStageByUri` that read bytes without an issueId and reply with `attachmentStaged`. On submit the bytes ride along on `createIssue.partial.attachments`, and the host replays them through `appendAttachment` after upserting the new ticket — same size + workspace guards apply.
- **`Closed` is a sidebar-only status.** It represents "won't do" tickets. The board never renders Closed tickets (no lane, no drawer). The sidebar hides them under the `All` filter; the dedicated `Closed` chip is the only way to view them. Agents cannot set status to `Closed` and cannot re-open a Closed ticket via MCP — `runUpdateTicketStatus` rejects both directions with the same shape as `Complete`.
- **Tags (`Issue.tags: string[]`) are free-form labels** edited in `IssueDetail` and rendered as colored chips in sidebar rows and board cards. Chip colors are derived deterministically from the tag name via `tagColor()` in [src/webview/Tags.tsx](src/webview/Tags.tsx) — no per-tag persistence. Sidebar and board drawer searches both match the query against tags in addition to title/id. `coerceTags()` in `types.ts` is the single normalization chokepoint: it trims, lowercases-for-dedup, and drops non-string / empty entries. Schema, host merge, MCP `create_ticket`, and the import path all funnel through it.
- **Description + verify-criteria text is auto-linkified.** `LinkedText` in [src/webview/IssueDetail.tsx](src/webview/IssueDetail.tsx) splits the body on a single regex covering `http(s)://`, `file:///`, `mailto:`, and workspace-relative `./` / `../` paths. Each anchor's click posts `openLink` (a new `WebviewToHost` variant) which the host routes through a single `openLink()` helper in `extension.ts`: `http`/`https`/`mailto` → `vscode.env.openExternal`; `file`/`vscode` schemes and `./`-prefixed paths → `vscode.commands.executeCommand("vscode.open", ...)`. Unknown schemes are rejected with a warning toast — never silently followed.
- **Ticket links (`Issue.links: TicketLink[]`) are single-source and typed.** A `TicketLink` is `{ targetId, kind }` where `kind ∈ {blocks, child-of, relates-to}` (`LINK_KINDS` in `types.ts`). Only the *source* ticket persists its outbound links; a target's "Linked by" view is **derived on read** by scanning every issue and inverting the kind via `INVERSE_LINK_KIND` (`blocks→blocked-by`, `child-of→parent-of`, `relates-to→relates-to`). There is no dual-write — deleting a link from A removes it everywhere; deleting ticket A also scrubs inbound links pointing at it (explicit `DELETE FROM issue_links WHERE target_id = ?` in `storage.remove`, since sql.js's FK cascade is unreliable across `exportDb`). `coerceLinks()` in `types.ts` is the shape/dedup/self-link chokepoint (format only — it can't see the store); `validateLinks()` in `extension.ts` is the cross-issue chokepoint that drops unknown-id targets (needs a `knownIds` set). Both `mergeIssueUpdate` (UI edits, with `knownIds`) and MCP `create_ticket` funnel through them. The webview editor is [src/webview/LinkEditor.tsx](src/webview/LinkEditor.tsx) (typeahead by `#id`/title + a kind `<select>`); pure helpers (`deriveInbound`, `buildGraphModel`, `searchIssuesForLink`) live in [src/webview/linkModel.ts](src/webview/linkModel.ts) — **note the lowercase name**: it must NOT collide with `Links.tsx` (the chip components), or esbuild's case-insensitive resolver breaks the build. **Agents may set links only at `create_ticket` time; `update_ticket_progress` cannot touch them** (same policy as tags). MCP `publicView` exposes both `links` (outbound) and derived `inboundLinks`.
- **The Graph webview is the third mode.** `window.__DOSTUFF_MODE__` is `"sidebar" | "board" | "graph"`; [src/webview/index.tsx](src/webview/index.tsx) dispatches on it. [src/graphProvider.ts](src/graphProvider.ts) is a singleton `WebviewPanel` (mirrors `BoardPanel`) launched by `dostuff.openGraph`. [src/webview/Graph.tsx](src/webview/Graph.tsx) renders the link network in hand-rolled SVG with `d3-force` (layout-only dep) for positioning — the sim is run synchronously (`stop()` + `tick(280)`) on shape change and kept in a ref for drag-time reheating. Clicking a node posts `revealTicket`, routed through the `dostuff.revealTicket` command which fans out to the sidebar (opens the detail overlay) and board.

## Important files when extending

- **Adding a new MCP tool** → edit `src/mcpServer.ts`: register the tool inside `registerTools`, and extract its handler to a standalone exported function (mirror the existing `runGetTicket` / `runCreateTicket` / etc. pattern) so it can be tested directly. Add tests in `src/mcpServer.test.ts`.
- **Adding a new webview message** → add the new variant to the `HostToWebview` or `WebviewToHost` discriminated union in `src/types.ts`, then handle it on both sides: in `src/webview/messaging.ts` (webview-side dispatch) and in the relevant provider (`sidebarProvider.ts` or `boardProvider.ts` on the host side).
- **Changing the schema** → update `src/types.ts`, then update the normalizer in `src/storage.ts` so legacy tickets without the new field still load correctly.

## Testing the webview manually

There is no headless test harness for the React UI. `bun test` and `bunx tsc --noEmit` only catch host-side, MCP, and schema regressions — they do not exercise the webview. After any non-trivial webview change, walk through `SMOKE-TEST.md` in an Extension Development Host (F5). The smoke test covers the sidebar, board drag-and-drop, lane cap enforcement, import/export, and the MCP HTTP endpoint end-to-end.
