# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Core tenet: storage backward compatibility

**Every change must load ticket data written by any prior version of the extension without error or data loss.** Users upgrade in place. Three persistence surfaces are all part of the contract: the SQLite DB at `<storagePath>/dostuff.db` (sql.js), the `globalState` fallback when no workspace is open, and the legacy `<id>.json` ticket files the one-shot migration still reads. The loader — not the writer — is the compatibility boundary. Concretely:

- **Schema changes are additive only.** Add new optional fields and new tables; never rename, retype, or repurpose an existing column/field. If a field's meaning must change, introduce a new one and migrate. (Precedent: `tags`, `links` (+ the `issue_links` table), and `attachments` were *added*; an older DB or JSON without them loads with empty defaults. `pendingClose` (+ the `issue_pending_close` table) added a 0-or-1 relation defaulting to `null`. Sync added `guid`/`updatedAt` on issues, optional `tasks[].updatedAt`, and the `sync_tombstones` table — all with lazy/derived defaults. Most recently `commits` (+ the `issue_commits` table) added an append-only `{sha, at}` list defaulting to `[]`; note its downgrade caveat: an older build's edit rewrites the ticket without the relation (delete-cascade, no re-insert), so commits recorded on that ticket are lost — load never breaks, same accepted class as the sync-field caveat below.)
- **New SQL tables/columns use `CREATE TABLE IF NOT EXISTS` and are read with `?? []`.** `db.exec(SCHEMA_DDL)` runs on every open, so a `main`-era DB gains the new (empty) table on first load by this build; `hydrateFromDb` must default a missing relation to `[]` (e.g. `linksBySource.get(row.id) ?? []`) — or to `null` for a 0-or-1 relation (`pendingCloseByIssue.get(row.id) ?? null`). **Columns on existing tables use the guarded-`ALTER TABLE ADD COLUMN` pattern** in `initSqlite` (catch and swallow "duplicate column name"; also add the column to the CREATE so fresh DBs skip the ALTER), read with `??` fallbacks (`row.guid ?? deriveGuid(row.id, row.created_at)`, `row.updated_at ?? row.created_at`). Adding a table need not bump `SCHEMA_VERSION`; only bump it when an upgrade requires a data backfill, and keep the "DB newer than this build → warn and continue" path intact so a downgrade never crashes. Downgrade caveat for sync fields: an older build's INSERT NULLs `guid`/`updated_at`, so an edit made there can lose LWW on the next sync (falls back to `createdAt`) — ticket *identity* stays safe because `deriveGuid` re-derives deterministically.
- **`storageCore.ts`'s `normalize()` is the single migration chokepoint for object-shaped input** (legacy JSON + `globalState`; re-exported through `storage.ts`). Every new field must be defaulted there for raw objects that lack it (`coerceTags(raw.tags)` / `coerceLinks(raw.links)` / `Array.isArray(...) ? ... : []`). Never read a new field off a loaded ticket without a default.
- **Coercers accept `unknown` and return a safe empty value on bad/missing input** (`coerceTags` / `coerceLinks` / `coerceAttachments` in `types.ts` all guard `if (!Array.isArray(input)) return []`). They must never throw on legacy data.
- **New `Status`/`Priority`/`type` enum values must degrade gracefully.** `normalize()` coerces unrecognized enum values to a safe default (`Thinking` / `Regular` / `Chore`) rather than crashing, so a ticket written by a newer build still loads on an older one.
- **When you touch the schema, prove it.** Add a `storage`/`types` test that feeds a minimal legacy object (only the old required fields) through `normalize()` — and, for a new table, hydrates a DB created without it — and asserts the new fields default correctly. This is non-negotiable for any schema PR.

## Project

DoStuff is a VSCode extension built with Bun + esbuild. Two bundles ship from one source tree: `dist/extension.cjs` for the extension host (CommonJS, required by VSCode's loader) and `media/index.js` + `media/styles.css` for the webview UI (browser IIFE). The webview is React 18 with `react-window` v1.8.x for list virtualization. The extension also runs a loopback-only HTTP MCP server exposing the active ticket queue to coding agents — the port is OS-assigned by default (`dostuff.mcp.port`, default `0`); agents discover it via the registry at `~/.config/dostuff/instances.json` (see README "Multi-workspace agent discovery"). The agent workflow prompt (`src/workflowPrompt.ts`) is served once per connection as MCP initialize `instructions` (plus the `dostuff://instructions/workflow` resource and `workflow` MCP prompt); tool responses embed only the one-line `WORKFLOW_POINTER`.

The prompt is also the only place the **write-terse contract** for agent-authored ticket prose lives (record notes: one line, ~15 words, facts and outcomes; descriptions: 1-2 sentence lead). It is there because agent prose is replayed on every later read of a ticket — no single tool description covers all write paths. The schema enforces the floor: `recordEntry` / `note` cap at 500 chars and `description` at 10,000, and an over-long value is *rejected*, not truncated. These are **input** caps only — a longer description written by an older build (or by a human in the UI) still loads and is served unchanged. Tests pin both the prompt rule and the cap.

**The workflow prompt has a hard byte budget — `PROMPT_BYTE_BUDGET` (1800), asserted in tests.** Claude Code truncates MCP server instructions *and* each tool description at 2KB, silently, so an overrunning prompt loses its **tail** — historically the OBE-close flow and the field-immutability contract, i.e. the rules least safe to drop. Two consequences for anyone editing that file: keep additions inside the budget or move the detail into a tool's own `description` (each gets its own 2KB), and remember Claude Code **defers MCP tool schemas by default** (tool search), so the instructions — not `tools/list` — are what actually costs context every session and what decides whether an agent searches for these tools at all. Lead with what the server is; carry only rules no single tool description can.

## Commands

- `bun run build` — bundle both extension and webview via esbuild.
- `bun run watch` — same in continuous watch mode.
- `bun test` — run all tests with Bun's built-in test runner.
- `bun test -t "<name>"` — run a single test by name pattern.
- `bun run package` — build, then produce a `.vsix` via `@vscode/vsce`.
- `bun run clean` — remove `dist/` and the webview output files in `media/`.

Press `F5` in VSCode (or `Run and Debug > Run Extension`) to launch an Extension Development Host with the current build.

## Architecture

DoStuff is a **vscode-free core** wrapped by host adapters. The core — `src/storageCore.ts` (`IssueStoreCore`: sql.js, `normalize()`, mutator/tombstone chokepoints, attachment IO, the serialized+coalescing export queue), `src/mcpServer.ts` (tools/resources/prompt, agent gates, the per-store write queue that serializes mutating tool dispatch), `src/mcpHost.ts` (config/logger/workspace seams + coercers), `src/gitSync.ts`, `src/events.ts`, plus the always-pure `types.ts`/`syncMerge.ts`/`gitPlumbing.ts`/`mcpRegistry.ts`/`mcpLimits.ts`/`workflowPrompt.ts` — must never import `vscode`. **The `dist/server.cjs` esbuild target is the guard**: it has no `vscode` external, so a stray import fails `bun run build` loudly. Two hosts wire it: the **VSCode extension** (`src/extension.ts` + `src/storage.ts` (`IssueStore` adapter: workspace-folder/config resolution, `globalState` KV, `workspace.fs`-backed `StorageFs`, `vscode.Uri` wrappers) + `src/mcpHostVscode.ts` (settings snapshot, workspaceId with override, OutputChannel logger)), and the **headless CLI** (`src/serverMain.ts` → `dist/server.cjs`: flags > `DOSTUFF_*` env > JSONC-tolerant `.vscode/settings.json` parse > defaults, singleton gate per workspace, same registry). The **webview bundle** (`src/webview/*.tsx`, React 18) talks to the extension host over the typed `HostToWebview` / `WebviewToHost` protocol; the **esbuild pipeline** emits three bundles (CJS extension, CJS headless server, browser-IIFE webview). `src/types.ts` is the canonical schema.

See [docs/architecture.md](docs/architecture.md) for the full breakdown — per-module responsibilities, cross-webview drag, list virtualization, and the `vscode` mock aliasing used in tests. The headless/core split's design record is [docs/plans/headless-server/00-overview.md](docs/plans/headless-server/00-overview.md), including the four-layer concurrency model (export queue L1, write serialization L2, `expectedUpdatedAt` CAS L3, singleton gate + sync L4).

**Git-native ticket sync (opt-in).** With `dostuff.sync.enabled` off (the default), the `IssueStore` is single-writer exactly as before: sql.js in-memory, wholesale `dostuff.db` rewrites, no external-change detection, and two VSCode windows on one workspace can clobber each other. With sync **on**, ticket state also lives as git objects under a hidden ref (`refs/dostuff/state`, never the worktree): `src/syncMerge.ts` (pure state-level LWW merge on `updatedAt` with content-hash tiebreak, per-element task/attachment LWW + tombstones, deterministic `DS-NNN` renumbering, 90-day tombstone GC), `src/gitPlumbing.ts` (vscode-free `git` CLI wrapper — CAS ref updates, batch object IO), and `src/gitSync.ts` (controller: debounced outbound commits, 15s tip poll that fixes same-machine two-window clobbering, fetch→merge→apply→push cycle). Every store mutation stamps `updatedAt`/`guid` and records deletion witnesses in `sync_tombstones` via the `upsert` chokepoint; sync applies remote state through `applySync` with `preserveTimestamps` (never restamping). The design record lives in [docs/plans/ticket-sync/00-overview.md](docs/plans/ticket-sync/00-overview.md) — read it before touching `IssueStore` mutators, id minting, persistence, or the merge rules.

### Agent write boundaries (MCP) — non-negotiable

These status-gating rules are the safety contract for MCP-connected agents: they constrain *which states an agent may edit and how*. Keep them front-of-mind; the code enforces each in multiple layers by design.

- **New tickets always land in `Thinking`.** Both the UI new-issue modal and the MCP `create_ticket` tool start them there. Agents *may* now promote a ticket out of `Thinking` into an active lane (see `update_ticket_status`), but nothing is ever created directly into an active lane, and only a human can accept a ticket (`Complete`) or approve a close (`Closed`).
- **`update_ticket_status` (MCP) allows any non-terminal ↔ non-terminal move.** Target (`AGENT_WRITABLE_STATUSES`) and source (`AGENT_VISIBLE_STATUSES`) are both {Thinking, Planned, Working, Verification} — an agent may promote Thinking→active, move among the active lanes, or demote a ticket back to Thinking. Complete/Closed stay untouchable in either direction. The lane cap applies to every active-lane target; Thinking is uncapped. (The host's `applyIssueUpdate` chokepoint is only cap-gated; the UI deliberately gives humans a freer hand.)
- **`update_ticket_description` (MCP) edits only the `description`** (plus one `record` entry). Gate is `AGENT_VISIBLE_STATUSES`; Complete and Closed are rejected. This is the *only* MCP path that changes prose — title, priority, type, and verifyCriteria stay immutable over MCP. Replace-shaped, so it accepts the optional `expectedUpdatedAt` CAS token: stale → rejection embedding the fresh state (never a silent lost update); absent → legacy last-writer-wins.
- **`update_ticket_progress` (MCP) only mutates `tasks[].done`, appends one `record` entry, and may append one commit sha to the append-only `commits` list** (the optional `commit` param — hex-validated, lowercased, deduped; nothing over MCP ever removes an entry). Title, priority, type, and verifyCriteria are immutable through this tool (the description is edited via `update_ticket_description`). Gate is `AGENT_VISIBLE_STATUSES`; Complete and Closed are rejected. Commit subjects/files are never stored — the host derives them lazily from the workspace repo for the UI (`src/commitDetails.ts`). The response echoes only `tasksChanged` (the ids this call touched) plus `tasks: {total, done}` — never the whole task list.
- **`update_ticket_draft` (MCP) reshapes a draft's `tags`, `links`, and `tasks` — `Thinking`-only.** While a ticket sits in an active lane its tags/links/tasks are frozen over MCP; agents fall back to `update_ticket_progress` for done-toggles + records (and `update_ticket_description` for prose). Note the lock is now *soft*: an agent can demote a ticket to Thinking, reshape it, and re-promote — the round-trip is visible in `statusHistory`/`record`, so it's auditable rather than forbidden. Accepts the same optional `expectedUpdatedAt` CAS token as `update_ticket_description`.
- **Mutating MCP tool calls are serialized per store** (write queue in `registerMcpTools`) — skill callers are bare curl with no client-side serialization, so parallel subagents produce genuinely concurrent mutations. Reads stay concurrent. Never add an `await` between a handler's `store.get()` and its `store.upsert()` assuming atomicity from elsewhere; the queue is what makes read-modify-write safe.
- **Active lanes (Planned, Working, Verification) are each capped at 6 open tickets.** Enforced independently in three places: the board UI drop handler, the host's `applyIssueUpdate` (the authority), and the MCP `update_ticket_status` tool. Agents can now consume this capacity via Thinking→active promotions — still bounded by the cap.
- **Both terminal states require human approval, via two distinct request flows.** Agents cannot set `Closed` or `Complete` directly. `request_ticket_close` (MCP) flags a ticket as **OBE / no longer needed** — `pendingClose` with `target: "Closed"`; approval moves it to `Closed` ("won't do"). `request_ticket_complete` (MCP) signals **finished work** — `pendingClose` with `target: "Complete"`, allowed **only from `Verification`**; approval moves it to `Complete` and stamps `resolvedAt`. Neither changes status itself; a human approves or denies via the `dostuff.resolveClose` command in the DoStuff UI (approve honors the request's target). The two flows are deliberately distinct so ticket history distinguishes dropped work from accepted work. A request with the other target replaces the pending one (recorded — auditable). Legacy `pendingClose` rows without `target` mean `Closed`. Agents still cannot re-open a Closed or Complete ticket. The board never renders Closed tickets; the sidebar has an "Awaiting decision" filter for pending requests.
- **Applying remote merged sync state is *not* an agent write.** MCP status gating does not apply to it (a remote human may legitimately have set `Complete`/`Closed`), but every inbound ticket passes `coerceWireTicket` shape-coercion plus `normalize()` before touching the store.

The remaining UI/implementation rules — Thinking-drawer click vs. Shift+Click, attachment storage internals, tag chip rendering, description auto-linkification, the single-source ticket-link model, and the graph webview mode — live in [docs/workflow-rules.md](docs/workflow-rules.md).

## Important files when extending

- **Adding a new MCP tool** → edit `src/mcpServer.ts`: register the tool inside `registerTools`, and extract its handler to a standalone exported function (mirror the existing `runGetTicket` / `runCreateTicket` / etc. pattern) so it can be tested directly. Add tests in `src/mcpServer.test.ts`. Keep the `description` under 2KB (a test enforces it), and mark a pure read with `annotations: { readOnlyHint: true }` so Claude Code can dispatch it concurrently instead of serializing it against other calls.
- **Changing what a ticket read returns** → `publicView` / `summaryView` / `statusView` in `src/mcpServer.ts`. Reads are deliberately lean: `record` is windowed, `commits` and long `verifyCriteria` are demoted behind `include`, and anything withheld is named in `omitted` using the exact `include` spelling. Add the new field's byte cost to `src/measure.bench.test.ts` rather than guessing — it prints a per-key breakdown on every run, and past estimates in this area were wrong by 2× in both directions.
- **Adding a new webview message** → add the new variant to the `HostToWebview` or `WebviewToHost` discriminated union in `src/types.ts`, then handle it on both sides: in `src/webview/messaging.ts` (webview-side dispatch) and in the relevant provider (`sidebarProvider.ts` or `boardProvider.ts` on the host side).
- **Changing the schema** → update `src/types.ts`, then update the normalizer in `src/storageCore.ts` so legacy tickets without the new field still load correctly (see the storage backward-compatibility tenet above).
- **Touching the core** (`storageCore.ts`, `mcpServer.ts`, `mcpHost.ts`, `gitSync.ts`, `serverMain.ts`, or anything they import) → no `vscode` imports; `bun run build`'s `server.cjs` target fails on one. Host-specific behavior goes through the seams: `StorageHost`/`StorageFs`/`KvStore` (storage), `McpConfigProvider`/`ToolHost`/`Logger` (`mcpHost.ts`), `GitSyncOptions.notify` (sync). New `dostuff.*` settings must be added to **both** resolvers — `mcpHostVscode.ts`/`storage.ts` and `serverMain.ts`'s `resolveServerConfig` — or the two hosts drift.
- **Changing MCP tools, field caps, or workflow rules** → also update the Claude Code agent skill in `skills/dostuff-tickets/` (SKILL.md, `references/tools.md`, and the cap table in `scripts/dostuff.sh`). `src/agentSkill.test.ts` is the drift guard: it derives the tool roster from `registerMcpTools` and the caps from `FIELD_LIMITS` (`src/mcpLimits.ts` — the single home for input caps; the zod schemas reference it), so an undocumented tool or a changed cap fails CI until the skill follows. Skill releases ride the version in `package.json`: `.claude-plugin/plugin.json` must match it (test-pinned), and the extension auto-refreshes command-installed copies on activation via the version+hash marker in `src/skillInstall.ts` — so bump `package.json` version whenever the skill changes, or installed copies won't update. To dogfood the skill locally, symlink it: `ln -s ../../skills/dostuff-tickets .claude/skills/dostuff-tickets` (`.claude/` is gitignored, so the link stays local).

## Testing the webview manually

There is no headless test harness for the React UI. `bun test` and `bunx tsc --noEmit` only catch host-side, MCP, schema, and sync regressions — they do not exercise the webview. After any non-trivial webview change, walk through [SMOKE-TEST.md](SMOKE-TEST.md) in an Extension Development Host (F5), covering the sidebar, board drag-and-drop, lane cap enforcement, import/export, the MCP HTTP endpoint end-to-end, and (when touched) the git sync walkthrough.
