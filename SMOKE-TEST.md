# DoStuff Smoke Test

Manual end-to-end walkthrough for the Extension Development Host. `bun test` and `tsc` cover host-side units, MCP handlers, and storage; this doc covers anything the React webview, drag/drop, the MCP HTTP endpoint, or the JSON → SQLite migration does end-to-end.

## Prereqs

- `bun run build` succeeded — verify `dist/extension.cjs` AND `dist/sql-wasm.wasm` both exist. The WASM blob is what makes the SQLite backend run; if it's missing, activation will throw on first ticket write.
- Two scratch workspaces ready: an **empty** one (no `.vscode/dostuff/`) and a **legacy** one (has `.vscode/dostuff/*.json` files from a pre-SQLite build of DoStuff). If you don't have a legacy workspace lying around, see "§1 Seed a legacy workspace" below for a 30-second recipe.

## §1 Seed a legacy workspace (only needed once)

Skip if you already have a workspace with old `.vscode/dostuff/<id>.json` files. Otherwise:

```bash
mkdir -p /tmp/dostuff-legacy/.vscode/dostuff
cat > /tmp/dostuff-legacy/.vscode/dostuff/DS-001.json <<'EOF'
{
  "id": "DS-001",
  "number": 1,
  "title": "Legacy ticket A",
  "type": "Feature",
  "priority": "Regular",
  "status": "Planned",
  "description": "Pre-SQLite ticket. Should migrate.",
  "tasks": [{ "id": "t1", "text": "first task", "done": false }],
  "tags": ["zebra", "alpha"],
  "verifyCriteria": "",
  "createdAt": "2025-05-01T00:00:00.000Z",
  "resolvedAt": null,
  "statusHistory": [{ "status": "Planned", "at": "2025-05-01T00:00:00.000Z", "by": "user" }],
  "record": [],
  "attachments": []
}
EOF
cat > /tmp/dostuff-legacy/.vscode/dostuff/DS-002.json <<'EOF'
{
  "id": "DS-002",
  "number": 2,
  "title": "Legacy ticket B",
  "type": "Bug",
  "priority": "High",
  "status": "Working",
  "description": "Second pre-SQLite ticket.",
  "tasks": [],
  "tags": [],
  "verifyCriteria": "",
  "createdAt": "2025-05-02T00:00:00.000Z",
  "resolvedAt": null,
  "statusHistory": [
    { "status": "Planned", "at": "2025-05-02T00:00:00.000Z", "by": "user" },
    { "status": "Working", "at": "2025-05-02T01:00:00.000Z", "by": "user" }
  ],
  "record": [],
  "attachments": []
}
EOF
# A deliberately malformed file — should be logged and skipped, not crash activation.
echo "{not json,,,," > /tmp/dostuff-legacy/.vscode/dostuff/DS-099.json
```

## §2 Migration walkthrough (the critical path for this release)

This section verifies the one-shot JSON → SQLite migration. Run it the first time you ship the SQLite branch and any time you touch `IssueStore.initSqlite` or `migrateLegacyJsonFiles`.

1. **Open the legacy workspace.** `code /tmp/dostuff-legacy` (or whichever folder has your legacy tickets) and `F5` to launch the Extension Development Host with the freshly built extension.

2. **Open the DoStuff Storage output channel.** *View → Output → DoStuff Storage*. You should see exactly one migration line, e.g.
   ```
   [2026-05-18T...] Migrated 2/3 ticket(s) from JSON → SQLite in <N>ms.
   ```
   - `2/3` because `DS-099.json` is corrupt and should be skipped (and logged with a separate "Failed to parse DS-099.json during migration: …" line).
   - If the count doesn't match the number of valid JSON files: stop. Migration is wrong. Check the output channel for parse failures.

3. **Inspect the storage folder on disk.** Open a terminal:
   ```bash
   ls -la /tmp/dostuff-legacy/.vscode/dostuff/
   ls -la /tmp/dostuff-legacy/.vscode/dostuff/legacy-json-backup/
   ```
   Expect:
   - `dostuff.db` present (size > 0).
   - `.gitignore` present, content is `# Auto-generated by DoStuff. Ticket data is local to this clone.\n*\n!.gitignore\n`.
   - **No** `*.json` files at the top level. All migrated AND corrupted files are now under `legacy-json-backup/` — including `DS-099.json` (the corrupt one).
   - `legacy-json-backup/` contains the original three files byte-for-byte (open one and diff against your seed if paranoid).

4. **Open the sidebar.** Click the DoStuff icon in the activity bar. You should see:
   - `DS-001` "Legacy ticket A" — Planned, tags chips render in order **zebra**, then **alpha** (insertion order, NOT alphabetical — alpha would come first if order broke).
   - `DS-002` "Legacy ticket B" — Working.
   - `DS-099` is **not** in the list (it was the corrupt one).

5. **Open the board.** Command palette → *DoStuff: Show Board*. Verify:
   - DS-001 sits in the **Planned** lane.
   - DS-002 sits in the **Working** lane.
   - Drawers (Thinking / Complete / Closed) show their usual collapsed state.

6. **Open DS-001's detail view.** Click the card. Verify:
   - Description matches the seed text.
   - The one task ("first task") is present and not-done.
   - Tags render `zebra`, then `alpha` in the same order as the legacy JSON.

7. **Open DS-002's detail view.** Verify the status history shows two entries in chronological order: Planned → Working. Order matters — if SQLite hydration broke `ORDER BY position`, this would be flipped or randomised.

8. **Restart the Extension Development Host** (close it and re-`F5`). Expect:
   - Output channel does NOT show a second "Migrated X/Y" line. Migration is one-shot; the second activation should just open the existing `dostuff.db`.
   - All tickets still render correctly.
   - `legacy-json-backup/` is unchanged (no new files appeared, no files moved out).

9. **Sanity-check on a Git-tracked workspace.** Run `git status` from the legacy workspace root. The `.vscode/dostuff/` contents (including `dostuff.db` and the backup folder) should NOT appear as untracked. The auto-written `.gitignore` excludes them. If they do show up, the `.gitignore` either wasn't written or the user has a `dostuff.writeStorageGitignore` override.

## §3 Fresh-workspace sanity

Open the empty workspace, `F5` again.

1. Sidebar empty. Output channel shows no migration line (no `.json` files to migrate, no log entry expected).
2. Command palette → *DoStuff: New Issue…* → fill title, save. Sidebar updates. Disk now has `<workspace>/.vscode/dostuff/dostuff.db` and `.gitignore`. No `<id>.json` files anywhere.
3. Add another ticket; restart host; both persist.

## §4 Full feature walk (regression sweep)

Run these against either workspace once the storage path is verified.

### Sidebar
- Type-to-search filters tickets; the `All` chip shows everything except `Closed`; the `Closed` chip is the only way to see closed tickets.
- New Issue button opens the modal; Esc closes; Save lands the ticket in `Thinking`.
- Drag a sidebar row into the board. The board opens if it wasn't already, and lanes/drawers show a "Move to *lane*" overlay. Click a lane → ticket moves. Esc cancels mid-drag.

### Board
- Drag a card between Planned/Working/Verification — moves succeed.
- Try dragging a 7th card into a full active lane (Planned with 6 cards) — toast appears, drop is rejected, lane count stays 6.
- Shift+Click a Thinking-drawer card → promotes to Planned.
- Plain click a Thinking-drawer card → opens detail overlay, does NOT promote.
- Complete-drawer card click opens detail overlay only (no Shift+Click promotion shortcut).
- Closed cards do not appear on the board at all (no lane, no drawer).

### Detail panel
- Edit title/description/verifyCriteria — autosaves (or on blur, depending on `dostuff.autoSave`).
- Add a tag → chip appears in the row immediately. Add 3+ tags → 3rd+ collapse to dots in the sidebar row.
- Click a URL in description text (`http://…`, `mailto:`, `./relative.md`, `file:///abs`) — opens correctly via the right vscode command (browser vs editor).
- Unknown scheme (`weird://thing`) → warning toast, NOT silently followed.

### Attachments
- Drag-drop an image (< 10 MB) onto the detail panel — appears under Attachments, thumbnail renders.
- Drag-drop a file > 10 MB — rejected with a toast.
- Click attached image → preview opens. Click attached non-image → opens in VSCode via `vscode.open`.
- Delete an attachment → bytes on disk gone (`ls <workspace>/.vscode/dostuff/attachments/<id>/`).
- Delete the whole ticket → that ticket's entire `attachments/<id>/` folder is gone.
- Restart host. Attachments still visible. (Verifies the metadata round-tripped through SQLite and the bytes path is unchanged.)

### Import / export
- Export — produces a JSON file with `{version, exportedAt, issues: [...]}`.
- Wipe the workspace storage manually (close host, `rm -rf .vscode/dostuff/`), restart host, import the exported file. All tickets land back. Verify a sample ticket's tags + statusHistory + attachments metadata match what was exported.

### MCP HTTP server
- *Settings → DoStuff → MCP: Enabled* (or `dostuff.mcp.enabled: true`).
- Status bar entry shows the port. Hit `curl http://127.0.0.1:<port>/.well-known/mcp` (or use an MCP client) and exercise `list_issues`, `get_ticket`, `create_ticket`, `update_ticket_status`, `update_ticket_progress`.
- Try `update_ticket_status` against a ticket in `Thinking` — should be rejected. Try moving INTO `Thinking` from `Planned` — rejected. Same for `Complete` and `Closed` in either direction.
- Create-ticket via MCP → lands in `Thinking`; UI shows it in the Thinking drawer.

## §5 Failure modes to spot-check

These shouldn't happen, but each one has burned us before; eyeball each release.

- Open the DoStuff Storage output channel. Look for any `Failed to parse` / `Failed to move` / SQL error lines after a clean activation. None expected.
- `<workspace>/.vscode/dostuff/dostuff.db.tmp` should NOT linger after any mutation. If it does, the rename step failed at least once — investigate.
- Activate against a workspace whose `dostuff.db` is from a previous version of the extension (forward-compat). The `schema_meta` upgrade hook should run; tickets still load. (Hook is a no-op today; the test is that it doesn't crash.)

## When to update this doc

Add a row whenever you ship something that the unit suite can't cover — anything that involves the React webview, drag/drop, the MCP HTTP endpoint, or storage I/O at the system level. If you're changing storage internals, expand §2 with whatever case you'd want a future you to verify.
