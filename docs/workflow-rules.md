# Workflow rules the code enforces (UI / implementation)

> These rules are non-obvious from a fresh read of the code, so they live here.
> The **MCP agent write-boundary rules** (which states an agent may edit, and how
> — status gating, lane caps, `Closed` handling) are safety-critical and stay in
> [CLAUDE.md](../CLAUDE.md#agent-write-boundaries-mcp--non-negotiable). This file
> holds the remaining UI and implementation detail. For the architecture these
> rules sit on, see [architecture.md](architecture.md).

- **Thinking-drawer click is a detail view; Shift+Click is the promote action.** A plain click on a Thinking-drawer card opens the detail overlay (so humans can read the draft before triaging); Shift+Click promotes it to Planned via the same `setStatus` path used by drag. The Complete drawer has no promote shortcut — its cards only ever open the detail overlay.
- **Attachment writes go through the host, never `mergeIssueUpdate`.** Binary files live under `<storagePath>/attachments/<issueId>/<attachmentId><ext>` (sibling of the JSON tickets). The ticket JSON carries only `Attachment` metadata: `{ id, name, mimeType, sizeBytes, addedAt }`. The host's `appendAttachment` helper in `extension.ts` is the only path that mints new entries — `mergeIssueUpdate` reconciles `incoming.attachments` against `prior.attachments` by id and silently drops any unknown id, so the webview can reorder or delete but never inject. Uploads enforce `MAX_ATTACHMENT_BYTES = 10 MB` at the host edge and again at the MCP resource read. Deleting a ticket recursively removes its attachments folder. Image previews use `webview.asWebviewUri()` over an extended `localResourceRoots` pointing at the attachments dir; the URL is composed in the webview from `Settings.attachmentsBaseUri` + `<issueId>/<attachmentId><ext>`. Attachments are served to MCP clients as a new resource template `dostuff://attachments/{ticketId}/{attachmentId}` (base64 `BlobResourceContents`); `publicView()` decorates each `Attachment` with that URI so `get_ticket` lists them. The new-issue modal can stage attachments before the ticket exists: bytes from drag-drop go straight into modal state, while the + button and Remote-WSL URI drops round-trip through `pickAttachmentForStaging` / `stageAttachmentByUri` → host helpers `onPickForStaging` / `onStageByUri` that read bytes without an issueId and reply with `attachmentStaged`. On submit the bytes ride along on `createIssue.partial.attachments`, and the host replays them through `appendAttachment` after upserting the new ticket — same size + workspace guards apply.
- **Tags (`Issue.tags: string[]`) are free-form labels** edited in `IssueDetail` and rendered as colored chips in sidebar rows and board cards. Chip colors are derived deterministically from the tag name via `tagColor()` in [src/webview/Tags.tsx](../src/webview/Tags.tsx) — no per-tag persistence. Sidebar and board drawer searches both match the query against tags in addition to title/id. `coerceTags()` in `types.ts` is the single normalization chokepoint: it trims, lowercases-for-dedup, and drops non-string / empty entries. Schema, host merge, MCP `create_ticket`, and the import path all funnel through it.
- **Description + verify-criteria text is auto-linkified.** `LinkedText` in [src/webview/IssueDetail.tsx](../src/webview/IssueDetail.tsx) splits the body on a single regex covering `http(s)://`, `file:///`, `mailto:`, and workspace-relative `./` / `../` paths. Each anchor's click posts `openLink` (a new `WebviewToHost` variant) which the host routes through a single `openLink()` helper in `extension.ts`: `http`/`https`/`mailto` → `vscode.env.openExternal`; `file`/`vscode` schemes and `./`-prefixed paths → `vscode.commands.executeCommand("vscode.open", ...)`. Unknown schemes are rejected with a warning toast — never silently followed.
- **Ticket links (`Issue.links: TicketLink[]`) are single-source and typed.** A `TicketLink` is `{ targetId, kind }` where `kind ∈ {blocks, child-of, relates-to}` (`LINK_KINDS` in `types.ts`). Only the *source* ticket persists its outbound links; a target's "Linked by" view is **derived on read** by scanning every issue and inverting the kind via `INVERSE_LINK_KIND` (`blocks→blocked-by`, `child-of→parent-of`, `relates-to→relates-to`). There is no dual-write — deleting a link from A removes it everywhere; deleting ticket A also scrubs inbound links pointing at it (explicit `DELETE FROM issue_links WHERE target_id = ?` in `storage.remove`, since sql.js's FK cascade is unreliable across `exportDb`). `coerceLinks()` in `types.ts` is the shape/dedup/self-link chokepoint (format only — it can't see the store); `validateLinks()` in `extension.ts` is the cross-issue chokepoint that drops unknown-id targets (needs a `knownIds` set). Both `mergeIssueUpdate` (UI edits, with `knownIds`) and MCP `create_ticket` funnel through them. The webview editor is [src/webview/LinkEditor.tsx](../src/webview/LinkEditor.tsx) (typeahead by `#id`/title + a relationship `<select>`); pure helpers (`deriveInbound`, `buildGraphModel`, `searchIssuesForLink`, `RELATIONSHIP_OPTIONS`) live in [src/webview/linkModel.ts](../src/webview/linkModel.ts) — **note the lowercase name**: it must NOT collide with `Links.tsx` (the chip components), or esbuild's case-insensitive resolver breaks the build. The editor offers both forward and **inverse** relationships (`blocked by`/`parent of`): picking an inverse kind from ticket A targeting B stores the *forward* link on B (via the editor's `onAddInverse` → `postUpdateIssue` on B), so you can define "A is blocked by B" without opening B; inbound "Linked by" chips are removable for the same reason. The new-issue modal also offers inverse kinds: it stages them in `createIssue.partial.inboundLinks` (`{ sourceId, kind }[]`) and the host's `createIssue` handler appends `{ targetId: newId, kind }` to each source ticket right after minting the new id (the editor's inverse options appear whenever `onAddInverse` is supplied). **Via MCP, agents may set links at `create_ticket` time and reshape them (plus tags + tasks) while the ticket is in `Thinking` via `update_ticket_draft`; once triaged, links/tags/tasks are read-only over MCP** (same policy as tags — see the agent write boundaries in [CLAUDE.md](../CLAUDE.md)). MCP `publicView` exposes both `links` (outbound) and derived `inboundLinks`.
- **The Graph webview is the third mode.** `window.__DOSTUFF_MODE__` is `"sidebar" | "board" | "graph"`; [src/webview/index.tsx](../src/webview/index.tsx) dispatches on it. [src/graphProvider.ts](../src/graphProvider.ts) is a singleton `WebviewPanel` (mirrors `BoardPanel`) launched by `dostuff.openGraph`. [src/webview/Graph.tsx](../src/webview/Graph.tsx) renders the link network in hand-rolled SVG with `d3-force` (layout-only dep) for positioning — the sim is run synchronously (`stop()` + `tick(280)`) on shape change and kept in a ref for drag-time reheating. Toolbar sliders ("Forces") live-tune link distance, repulsion, and collision spacing by mutating the running sim's force params in place and reheating, so layouts re-relax without losing pan/zoom or manual drags. Clicking a node posts `revealTicket`, routed through the `dostuff.revealTicket` command which fans out to the sidebar (opens the detail overlay) and board. The free-text filter is **chain-preserving**: `graphNodeMatchesQuery` finds direct matches, then `visibleGraphNodeIds` (both in `linkModel.ts`) expands to the full connected component of each match (undirected reachability over the edge set) so a matched ticket never loses its context — non-match context nodes render dimmed, and the layout stays put (filtering hides/dims, never re-runs the sim) while *Fit to view* / the filter-change auto-fit frame the visible subset.
