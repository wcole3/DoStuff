# Architecture

> Detailed architecture reference for DoStuff. For the high-level overview and
> the rules a fresh read won't reveal, see [CLAUDE.md](../CLAUDE.md) and
> [workflow-rules.md](workflow-rules.md).

**Vscode-free core** (`src/*.ts`, host-agnostic). `storageCore.ts` exposes `IssueStoreCore`, which persists tickets to a SQLite DB (`sql.js`) at `<storageDir>/dostuff.db` (falling back to a host-provided KV when no storage dir exists), and one-shot-migrates any legacy `<id>.json` ticket files into it; its `upsert` chokepoint stamps `updatedAt`/`guid`, diff-stamps per-task `updatedAt`, and records deletion witnesses in `sync_tombstones`; its export queue serializes + coalesces the wholesale `dostuff.db` rewrites so overlapping mutations can never persist stale bytes last. Host seams (`StorageHost`: `storageDir()`, `wasmBinary()`, optional `KvStore`, optional `StorageFs` — default `node:fs`) keep it vscode-free. `mcpServer.ts` runs the loopback-only HTTP MCP server — OS-assigned ephemeral port by default, discoverable via the `~/.config/dostuff/instances.json` registry (`mcpRegistry.ts`) — with nine tools, four resources, one prompt, and the workflow contract served as initialize `instructions` (`workflowPrompt.ts` — kept under a hard byte budget, see below); mutating tool dispatch is serialized through a per-store write queue (bare-curl skill callers have no client-side serialization), and its host needs (`McpConfigProvider`, `ToolHost`, `Logger`) live in `mcpHost.ts`. `gitSync.ts` (below), `events.ts` (the minimal `Emitter`), `types.ts`, `syncMerge.ts`, `gitPlumbing.ts`, and `mcpLimits.ts` round out the core. `types.ts` is the canonical schema — it defines `Issue`, `Status`, `Priority`, the `HostToWebview` / `WebviewToHost` discriminated unions, `ACTIVE_LANE_CAP = 6`, and the `canMoveToActiveLane` helper.

**VSCode extension host.** `extension.ts` is the activation entry point — it registers the commands, wires up the sidebar and board providers, and starts/stops the MCP server and the git sync controller. `storage.ts` is the `IssueStore` adapter over `IssueStoreCore`: workspace-folder + `dostuff.storagePath` resolution, the `globalState` KV fallback, a `vscode.workspace.fs`-backed `StorageFs` (so remote workspaces keep their historical IO path), and `vscode.Uri` wrappers (`attachmentsDir`, `findAttachmentUri`) for the providers. `mcpHostVscode.ts` adapts live settings, the workspace folder (honoring `dostuff.mcp.workspaceOverride`), and an OutputChannel logger onto the `mcpHost.ts` seams. `sidebarProvider.ts` is a `WebviewViewProvider` for the activity-bar sidebar; `boardProvider.ts` is a singleton `WebviewPanel` for the full-tab board. `webviewHtml.ts` builds the CSP-nonced HTML shell. `ids.ts` mints task ids for both bundles.

**Headless CLI host** (`serverMain.ts` → `dist/server.cjs`). Serves the same MCP API against the same DB and registry with no VSCode: config resolves `flags > DOSTUFF_* env > JSONC-tolerant parse of <workspace>/.vscode/settings.json dostuff.* keys > defaults` (`--print-config` shows provenance), a per-workspace singleton gate refuses a workspace another live process serves (exit 3; `--takeover`), SIGINT/SIGTERM unregister cleanly, and `sql-wasm.wasm` resolves next to the bundle. Runs the same `GitSyncController` when `dostuff.sync.enabled` is set (`--no-sync` opts out). The `server.cjs` esbuild target has no `vscode` external — it is the build-time guard that the core stays vscode-free.

**MCP read shaping.** Agent-facing reads are deliberately lean, because every byte lands in a model's context. `publicView` windows the append-only `record` log to its newest `dostuff.mcp.recordLimit` entries (default 3), demotes commit shas to a `commitCount`, and truncates `verifyCriteria` past 2,000 chars — naming whatever it withheld in an `omitted` array that an agent hands straight back as `get_ticket`'s `include`. The `dostuff://tickets` collection serves `summaryView` rows (a per-ticket `excerpt` of the description's opening paragraph), not full bodies. Single-ticket payloads are serialized compactly. `src/measure.bench.test.ts` prints the byte cost of each of these on every `bun test` run — extend it rather than reasoning about payload size from first principles.

**Two Claude Code constraints shape this surface**, both documented at [code.claude.com/docs/en/mcp](https://code.claude.com/docs/en/mcp): server instructions and tool descriptions are **truncated at 2KB** (silently — a prompt that overruns loses its tail), and MCP tool schemas are **deferred by default** via tool search, so `tools/list` is not a per-session context cost while the instructions are. That is why `workflowPrompt.ts` leads with what the server is (the tool-search trigger) and carries only cross-tool rules, pushing per-tool mechanics into each tool's own `description`. One of those cross-tool rules is **write terse**: agent-authored record notes and descriptions are replayed on every later read of the ticket, so the prompt bounds them (one ~15-word line per note; a 1-2 sentence description lead) and the input schemas cap `recordEntry` / `note` at 500 chars.

**Git ticket sync** (opt-in, `dostuff.sync.enabled` default false; design record in [plans/ticket-sync/](plans/ticket-sync/00-overview.md)). Three modules: `syncMerge.ts` — pure (no vscode/git/IO/wall-clock) wire model + semilattice merge: per-ticket LWW on `(updatedAt, sha1(canonicalJson))`, per-element task/attachment LWW with persisted tombstones, links/tags/`pendingClose` wholesale from the winner, `statusHistory`/`record`/`commits` union, deterministic `DS-NNN` renumbering and 90-day tombstone GC. `gitPlumbing.ts` — vscode-free `git` CLI wrapper (argv arrays, never a shell; content over stdin/stdout; typed `GitError` taxonomy; CAS `update-ref`; one-process `cat-file --batch` reads and one-process `fast-import` writes — never a spawn per object, because a fork's cost scales with the host's RSS; timeouts armed at the child's `spawn` event so a stalled event loop can't fake one). `gitSync.ts` — the controller. Data flow: `store.onChange → 2s debounce → commitLocal (CAS ×5) → push follow-up` outbound; `15s tip poll + interval fetch → mergeStates → renumber → applySync (preserveTimestamps) → onChange → broadcast` inbound. Ticket state lives as git objects under `refs/dostuff/state` (fetch-tracking `refs/dostuff/remote`) — never in the worktree; attachment bytes ride the same tree at `attachments/<guid>/<attId>` (per-file cap, OID reuse).

**Webview bundle** (`src/webview/*.tsx`). The React 18 entry `index.tsx` reads `window.__DOSTUFF_MODE__` (set by the host shell) and renders `<Sidebar/>`, `<Board/>`, or `<Graph/>`. A shared `<IssueDetail/>` component handles the inline edit panel. `messaging.ts` wraps `acquireVsCodeApi()` and the host-to-webview message stream as a `useSyncExternalStore` hook so React components subscribe without leaking listeners. **The list is rows, not issues**: `init`/`issues` carry `IssueRow[]` (an `Issue` minus the append-only `record`/`statusHistory`/`commits`), every later edit arrives as an `issuesDelta` (upserted rows + removed ids; untouched rows keep identity), and `<IssueDetail/>` fetches the full body on demand via `fetchIssueDetail` → `issueDetail` (`useIssueDetail`, cached per id, refetched after a delta touches it). Host side, `webviewProtocol.ts` turns a `StoreChange` into the right message. Sorting (`sort.ts`, board lanes) precomputes one key per item instead of allocating `Date`s per comparison. The sidebar list and the Thinking/Complete drawers in the board use `react-window`'s `FixedSizeList` for virtualization; active board lanes are not virtualized (cap = 6). Drag-and-drop on the board uses the HTML5 native API — no third-party DnD library. **Cross-webview drag** (sidebar→board) is a pseudo-drag: native DnD doesn't reliably cross VSCode's webview iframe boundary, so the sidebar's `dragstart` posts an `externalDragStart` message; the host opens the board if needed and forwards the signal, and the board renders a click-absorbing "Move to *lane*" overlay (`bd-pick-overlay`) inside each lane/drawer. The actual mutation still flows through `setStatus` → `postUpdateIssue` → host `applyIssueUpdate`. Esc cancels.

**Build pipeline.** `scripts/esbuild.config.ts` exports three configs: `extensionConfig` (Node CommonJS target, `vscode` marked external), `serverConfig` (Node CommonJS target, **no** `vscode` external — the core's vscode-free build guard), and `webviewConfig` (browser IIFE target, no externals). `scripts/build-with-esbuild.ts` runs all three in parallel; `scripts/watch-with-esbuild.ts` watches all three. `vscode` is external in the extension config because VSCode injects the real API at load time. The webview never imports `vscode`. For tests, `tsconfig.json`'s `paths.vscode` alias redirects `import * as vscode from "vscode"` to the hand-rolled `mocks/vscode.ts` — so `tsc` and the IDE see the mock, but the runtime esbuild bundle leaves `vscode` external. Whenever you introduce a new `vscode.*` call in `src/`, add a stub to `mocks/vscode.ts` or test resolution will fail.
