# Architecture

> Detailed architecture reference for DoStuff. For the high-level overview and
> the rules a fresh read won't reveal, see [CLAUDE.md](../CLAUDE.md) and
> [workflow-rules.md](workflow-rules.md).

**Extension host** (`src/*.ts`, excluding `src/webview/`). `extension.ts` is the activation entry point — it registers the commands, wires up the sidebar and board providers, and starts/stops the MCP server and the git sync controller. `storage.ts` exposes `IssueStore`, which persists tickets to a SQLite DB (`sql.js`) at `<workspace>/<storagePath>/dostuff.db` (falling back to `globalState` when no workspace is open), and one-shot-migrates any legacy `<id>.json` ticket files into it; its `upsert` chokepoint stamps `updatedAt`/`guid`, diff-stamps per-task `updatedAt`, and records deletion witnesses in `sync_tombstones`. `sidebarProvider.ts` is a `WebviewViewProvider` for the activity-bar sidebar; `boardProvider.ts` is a singleton `WebviewPanel` for the full-tab board. `mcpServer.ts` runs a loopback-only HTTP MCP server — OS-assigned ephemeral port by default (`dostuff.mcp.port`, default `0`), discoverable via the `~/.config/dostuff/instances.json` registry (`mcpRegistry.ts`) — with nine tools, four resources, one prompt, and the workflow contract served as initialize `instructions`. `types.ts` is the canonical schema — it defines `Issue`, `Status`, `Priority`, the `HostToWebview` / `WebviewToHost` discriminated unions, `ACTIVE_LANE_CAP = 6`, and the `canMoveToActiveLane` helper. `webviewHtml.ts` builds the CSP-nonced HTML shell. `sampleData.ts` seeds the store on first activation.

**Git ticket sync** (opt-in, `dostuff.sync.enabled` default false; design record in [plans/ticket-sync/](plans/ticket-sync/00-overview.md)). Three modules: `syncMerge.ts` — pure (no vscode/git/IO/wall-clock) wire model + semilattice merge: per-ticket LWW on `(updatedAt, sha1(canonicalJson))`, per-element task/attachment LWW with persisted tombstones, links/tags/`pendingClose` wholesale from the winner, `statusHistory`/`record`/`commits` union, deterministic `DS-NNN` renumbering and 90-day tombstone GC. `gitPlumbing.ts` — vscode-free `git` CLI wrapper (argv arrays, never a shell; content over stdin/stdout; typed `GitError` taxonomy; CAS `update-ref`; one-process `cat-file --batch`). `gitSync.ts` — the controller. Data flow: `store.onChange → 2s debounce → commitLocal (CAS ×5) → push follow-up` outbound; `15s tip poll + interval fetch → mergeStates → renumber → applySync (preserveTimestamps) → onChange → broadcast` inbound. Ticket state lives as git objects under `refs/dostuff/state` (fetch-tracking `refs/dostuff/remote`) — never in the worktree; attachment bytes ride the same tree at `attachments/<guid>/<attId>` (per-file cap, OID reuse).

**Webview bundle** (`src/webview/*.tsx`). The React 18 entry `index.tsx` reads `window.__DOSTUFF_MODE__` (set by the host shell) and renders `<Sidebar/>`, `<Board/>`, or `<Graph/>`. A shared `<IssueDetail/>` component handles the inline edit panel. `messaging.ts` wraps `acquireVsCodeApi()` and the host-to-webview message stream as a `useSyncExternalStore` hook so React components subscribe without leaking listeners. The sidebar list and the Thinking/Complete drawers in the board use `react-window`'s `FixedSizeList` for virtualization; active board lanes are not virtualized (cap = 6). Drag-and-drop on the board uses the HTML5 native API — no third-party DnD library. **Cross-webview drag** (sidebar→board) is a pseudo-drag: native DnD doesn't reliably cross VSCode's webview iframe boundary, so the sidebar's `dragstart` posts an `externalDragStart` message; the host opens the board if needed and forwards the signal, and the board renders a click-absorbing "Move to *lane*" overlay (`bd-pick-overlay`) inside each lane/drawer. The actual mutation still flows through `setStatus` → `postUpdateIssue` → host `applyIssueUpdate`. Esc cancels.

**Build pipeline.** `scripts/esbuild.config.ts` exports two configs: `extensionConfig` (Node CommonJS target, `vscode` marked external) and `webviewConfig` (browser IIFE target, no externals). `scripts/build-with-esbuild.ts` runs both in parallel; `scripts/watch-with-esbuild.ts` watches both. `vscode` is external in the extension config because VSCode injects the real API at load time. The webview never imports `vscode`. For tests, `tsconfig.json`'s `paths.vscode` alias redirects `import * as vscode from "vscode"` to the hand-rolled `mocks/vscode.ts` — so `tsc` and the IDE see the mock, but the runtime esbuild bundle leaves `vscode` external. Whenever you introduce a new `vscode.*` call in `src/`, add a stub to `mocks/vscode.ts` or test resolution will fail.
